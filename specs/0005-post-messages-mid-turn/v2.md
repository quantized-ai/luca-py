Today a conversation that has active subagents is never projected. It's "parked" until all the subagents complete.

We want to completely change this behavior for three reasons:
1. we want to give LLMs the chance to run IMMEDIATELY after a subagent finishes
2. We want to allow users to post messages while the subagent runs (to steer the conversation)
3. We want to allow for "background" subagents (in the future, not this feature, but it's a reason)
4. We want to allow LLMs to cancel subagents they have spawned.

### 1. Allow LLM to intervene after every subagent finishes

Let's say we have this conversation:

```
UserMessage("Fix the bug in my code")
TurnStart()
AssistantMessage(tool_calls=tc1, tc2) # spawns 3 subagents
ToolExecution(tc1, COMPLETED, "Spawned subagent A")
ToolExecution(tc2, COMPLETED, "Spawned subagent B")
ToolExecution(tc2, COMPLETED, "Spawned subagent C")
ChildConversation(tc1, execution_result="I found a potential culprit in main.py")
ChildConversation(tc2, execution_result=None) # still running
ChildConversation(tc3, execution_result="Nothing in tests")
ToolExecution(tc1, *PRIVATE*, create_conversation_result, COMPLETED, "I found a potential culprit in main.py")
ToolExecution(tc3, *PRIVATE*, create_conversation_result, COMPLETED, "Nothing in tests")
```

As ChildConversation(tc1) finished early, we want the main conversation to be "re-awaken" and given the chance to do something or say something. In that case the main conversation has to be projected back to the LLM with something like:

```
messages = [
    {role: user, content:"Fix the bug in my code"},
    {role: assistant, reasoning=..., tool_calls=[tc1, tc2]}
    {role: tool, tool_call_id: tc1, content:"Spawned subagent tc1"},
    {role: tool, tool_call_id: tc2, content:"Spawned subagent tc2"},
    {role: user, content:"Partial Subagent update.<task id=tc1 status=completed completed_at="10 seconds ago">I found a potential culprit in main.py</task><task id=tc2 status=pending></task><task id=tc3 completed_at="0.1 seconds ago" status=completed>Nothing in tests</task>"}
]
```

while tc2 is still running. The projection is always a message with user role. Ideally, I'd like for partial updates (that is, for any projection happening while any subagent is running) to be contained all in a single user message noticing something like "This is a partial update" and include the completed_at just to let the LLM know the timing, that's it. But if it's not possible and projection has to project 1 message per entry that's ok as well.

For the record, this shouldn't affect "nested" max_depth>1 subagents, because the awake of the parent happens only when the child finished. So at most, when a childconversation finishes it can awake 1 conversation (only its direct parent). That can indeed trigger that the parent decides to terminate and complete causing a "chain reaction", but that is ok. the point is that the conversation at level 0 doesn't get awaken if the subagent at level 3 finishes.
```
Conversation - buys
    Conversation - busy
        Conversation - busy - X Gets awaken
            Conversation - busy
            Conversation - idle
        Conversation - busy
            Conversation - busy
            Conversation - busy
```

### 2. Allow users to post messages on conversations that are "waiting" on subagents

This is an "explicit" awakening of the conversation. Let's say we have this conversation with subagents running:

```
UserMessage("Fix the bug in my code")
TurnStart()
AssistantMessage(tool_calls=tc1, tc2) # spawn 2 subagents
ToolExecution(tc1, COMPLETED, "Spawned subagent A")
ToolExecution(tc2, COMPLETED, "Spawned subagent B")
ChildConversation(tc1, execution_result=None)
ChildConversation(tc2, execution_result=None)
--- main conversation is parked and waiting for children to finish---
```

The user posts a message:

```
UserMessage("Fix the bug in my code")
TurnStart()
AssistantMessage(tool_calls=tc1, tc2) # spawn 2 subagents
ToolExecution(tc1, COMPLETED, "Spawned subagent A")
ToolExecution(tc2, COMPLETED, "Spawned subagent B")
ChildConversation(tc1, execution_result=None)
ChildConversation(tc2, execution_result=None)
UserMessage("Once you're done, don't forget to update the docs")
```

We want now the parent conversation to resume. It could for example do something like:

```
UserMessage("Fix the bug in my code")
TurnStart()
AssistantMessage(tool_calls=tc1, tc2) # spawn 2 subagents
ToolExecution(tc1, COMPLETED, "Spawned subagent A")
ToolExecution(tc2, COMPLETED, "Spawned subagent B")
ChildConversation(tc1, execution_result=None)
ChildConversation(tc2, execution_result=None)
UserMessage("Once you're done, don't forget to update the docs")
AssistantMessage(reasoning=..., tool_calls=[Tool(id=tc3, update_todo, {..., "update docs"})])
ToolExecution(...)
```

### 3. WARNING: multiple conversation awakenings make this more complex

For the first time a projection can be started by reasons that are not deterministic. Before it was either a new message, or all the subagents are done.
Now a conversation can be "awaken" for several reasons, including user messages, tool execution finishing, or direct children subagent finishing.

We have to make sure that, as happens today with new user messages posted mid-turn, the projection happens ONLY if all the tool executions have completed. We can't send an LLM request if there are pending tool executions. If there's a pending tool execution, the user message posted mid turn or the fact that a child subprocess finishes will not immediately trigger an LLM call. Instead it'll be triggered once the tool execution finishes, and at that time the projection will include the UserMessage and the finished Child execution.

### 4. New tool: giving LLMs the possibility to stop subagents

This means we also have to define a new tool that allows LLMs to stop subagents. The tool has to be briefly defined in this way:

```python
class SubagentStop(BaseModel):
    model_config = ConfigDict(extra="forbid")

    is_subagent_stop: bool = True
    task_id: str
    reason: str | None = None


class StopSubagent(Tool):
    namespace = "contrib.subagents"
    name = "stop_subagent"
    description = ...
    tool_kind = ToolKind.OTHER
    output_schema = SubagentStop

    class Args(BaseModel):
        model_config = ConfigDict(extra="forbid")
        task_id: str = Field(
            description="The task id to stop. Has to match perfectly",
        )
        reason: str | None = Field(description="A short description of the reason to stop the task")

    async def execute(
        self,
        args: dict,
        session: AgentSession,
        conversation_id: str,
        *,
        cancellation_token: CancellationToken,
    ) -> ExecutionResult:
        task_id = args['task_id']
        reason = args.get('reason')

        payload = SubagentStop(task_id=task_id, reason=reason)
        return ExecutionResult(
            content=[TextContent(text=f"Stop subagent signal received for {task_id}. Reason: {reason}")],
            structured_content=payload.model_dump(),
        )

```

The mechanism is the same. The tool is defined outside but there's an agreed contract with the runner. Upon execution of the tool, the runner will stop the subagent.
The main question is of course how "deep" the LLMs can cancel subagents. My intuition tells me that they can only cancel their direct children, and nothing deeper, as I think it's the only visibility that they have to get projected, as they have to use the task_id. Furthermore, the `task_id` is optional when spawning today. The ExecutionResult returned by `contrib.subagents.tools.SpawnSubagent` is returning the `task_id` but this is a bit fragile as another implementation can forget to do so.

So we also need to offer a ListSubagentTool that just returns the subagents of the current turn (only direct children as we said) with the task id, description and prompt. Something like:

```
<task id={task_id} status={status} prompt={prompt}, description={description}></task>
<task id={task_id} status={status} prompt={prompt}, description={description}></task>
<task id={task_id} status={status} prompt={prompt}, description={description}></task>
<task id={task_id} status={status} prompt={prompt}, description={description}></task>
```

#### Meaning of "stopping a subagent"

As usual, we have to do "best effort" here, and accept that this can land mid-flight between a subagent that is doing work (receiving assistant messages, tool executions finishing, etc). Ideally, I'd like to "signal" that the Conversation (and the turn inside the conversation) is scheduled to be cancelled, and just allow the ToolExecutions to finish, without ANY new projections. If this is possible, this is my default preferred behavior. Once the ToolExecutions are done, the turn is closed and the conversation is closed. This will of course trigger an update to the parent id again (from our previous point).

We should also emit the `SubagentFinished` event as cancelled as well.

# Parallel Subagents — V2 scope

Three limits on subagent use: **how deep** they nest, **how many** one turn may
spawn, and **how many** may run at the same time. This document sizes each one
against the code as of `91f6be1`; every line reference is to that state.

Written to be read cold. §0 is the background needed for the rest; skip it if
you already know how the spawn handshake works.

**Recommendation: ship §1 and §2, hold §3.** §1 is already implemented and only
needs tests. §2 is the real cost control and is a few hours. §3 is the only one
that adds a scheduler to a runner that deliberately has none, so it should wait
for a workload that needs it.

---

## 0. Background — how subagents work today

A `luca` `AgentSession` holds **many conversations**, not one. `conversations`
is a dict keyed by id; `main_conversation_id` names the one the user talks to.
Every other conversation is a subagent. Each carries a `depth`: the main
conversation is `0`, a subagent spawned from it is `1`, and so on.

Spawning is **not** a special code path in the runner. It is a handshake
between an ordinary tool and the runner, in two halves:

| half | what is read | when | meaning |
|---|---|---|---|
| **gate** | `ToolSpec.output_schema` declares a property named `is_subagent_spawn` | before the model call, from the spec alone | this tool *can* spawn → subject to the caps |
| **handshake** | `ExecutionResult.structured_content["is_subagent_spawn"] is True` | after the execution completes | this call *did* spawn → create the child |

The two halves are deliberately asymmetric. `is_subagent_spawn` is a `bool`,
not a constant, so a spawn tool that decides at runtime **not** to spawn
returns the payload with `False` and no child is created — while still being
gated, because the gate reads the declaration, not the outcome
(`runner.py:3632-3654`).

The stock spawn tool is `SpawnSubagent` in
`luca/agent/contrib/subagents/tools.py`. It takes `prompt`, `description` and
an optional `task_id`, and returns the payload. It is contrib, not core: an
application can ship its own spawn tool and it gates identically, because the
runner matches the *declaration*, never a tool name.

### The gate

One predicate, written twice on purpose — once in contrib, once in core:

```python
# luca/agent/contrib/subagents/plugin.py:46
def spawn_gate_open(session: AgentSession, conversation_id: str) -> bool:
    config = session.session_config.runtime_config
    if not config.subagents_enabled:
        return False
    conversation = session.conversations.get(conversation_id)
    if conversation is None:
        return False
    return conversation.depth < config.subagents_max_depth
```

Three things derive from it, and they must never disagree:

1. `SubagentToolRegistry.get_tools` (`plugin.py:92`) filters out every
   spawn-declaring spec when it returns `False`.
2. `spawning_prompt_part` (`plugin.py:65`) contributes nothing under the same
   condition — a prompt that says "you can spawn" beside a tool list that
   withholds the tool would have the model try and fail.
3. Core's mirror `_spawn_gate_open` (`runner.py:1739`) backs it with two
   raising checks: `_verify_gate` (`runner.py:1750`) if a registry offered a
   spawn-declaring spec to a conversation that may not spawn, and `_spawn_one`
   (`runner.py:2604`) if a spawn payload arrives from one. Fail loud, because a
   silently filtered spec would make the cap invisible.

§2 adds a third clause to this predicate.

### The drive loop, in the order that matters here

Per iteration, for one conversation (`_drive_loop`, `runner.py:2241`):

```
1.  _create_executions(...)         # assistant message's tool calls → ToolExecution entries
2.  decide approvals, then _dispatch_batch(ready)
2b. _spawn_children()               # completed payloads → child conversations
2c. _resolve_children()             # finished children → results back into the parent
3.  park if anything awaits approval / while any child is unresolved
4.  _collect_tools() → get_tools + _verify_gate, then call the model
```

Two properties matter for §2:

- **Step 4 only runs when every execution in the open turn is terminal.** So at
  the moment the gate is evaluated, nothing is in flight and the spawn count is
  stable.
- **Step 1 persists sequentially.** `_create_executions` (`runner.py:3045`)
  asks the registry for one draft per tool call *concurrently*, then appends
  the drafts in a plain `for` loop **in model-request order**. When it appends
  call *k*, calls *1…k-1* of the same assistant message are already in the
  session. It also already supports **terminal-at-birth**: a draft whose status
  is not PENDING is never dispatched and goes straight to
  `_finalize_undispatched` (`runner.py:1644`), which emits the one
  `ToolExecuted` the "every tool call produces exactly one tool output"
  invariant requires.

## 1. `subagents_max_depth` > 1

**Status: already works. The lift is tests plus a stale comment.**

`RuntimeConfig.subagents_max_depth` defaults to `1` and `models.py:1008` says
it is "the only supported value in V0". That is no longer true.

Verified empirically. A throwaway test (written, run, deleted) with
`subagents_max_depth=2`:

```python
faux.set_responses([
    assistant([spawn_call("child work", "child", call_id="tc1")]),   # main  → child
    assistant([spawn_call("leaf work",  "leaf",  call_id="tc2")]),   # child → grandchild
    assistant([text("leaf done")]),                                  # grandchild answers
    assistant([text("child done")]),                                 # child answers
    assistant([text("all done")]),                                   # main answers
])
session = subagent_session(max_depth=2)
runner  = DeterministicRunner(session, tool_registry=SubagentRegistry(), provider=faux)
runner.post_message("go")
async with runner.run() as run:
    _ = [event async for event in run]
```

Result: conversation depths `[0, 1, 2]`, results flowed leaf → child → parent
(the parent's last model call carried `<task id=tc1>child done</task>`), and
`runner.idle()` was `True`. Nothing needed changing but the config value.

Why it already holds — every mechanism on the path is recursive by
construction:

| mechanism | where | why it is depth-generic |
|---|---|---|
| the gate | `runner.py:1739`, `plugin.py:46` | `conversation.depth < max_depth` — no assumption that the cap is 1 |
| event fan-in | `AgentRun._forward`, `runner.py:739` | each run pushes its events to *its* parent's inbox, and the parent forwards on; the chain is as long as the tree |
| subtree lookup | `_lookup`, `_parked_handle` | already recursive |
| resume after a gate | `_begin_run` → `_restart_unresolved_children`, `runner.py:1291` | runs for **every** run, so restarting a child restarts that child's own children |
| step limits | `_step_limits`, `runner.py:3551` | asks only `depth == 0` |
| compaction | main conversation only | unaffected at any depth |

### Work

1. Delete the "only supported value in V0" comment (`models.py:1008`) and the
   same claim in `AGENTS.agent.md:453` and `docs/agent/13-subagents.md`.
2. Decide the default. Staying at `1` keeps nesting opt-in; Claude Code
   defaults to 3. Recommend keeping `1` and documenting the knob — nesting
   multiplies cost and we have no per-depth budget (see below).
3. Tests. Nothing in `tests/agent/subagents/` currently goes past depth 1:
   - grandchild spawn, end to end (the probe above, as a real test)
   - the spawn tool withheld at the leaf: `max_depth=2`, conversation at depth 2
   - `_verify_gate` raises when a registry leaks a spawn spec to a depth-2 leaf
   - cancel cascading three levels
   - reload mid-tree with a grandchild still unresolved
   - an approval gate on a grandchild: answered, resumed, parent unblocks

**Estimate: half a day, nearly all tests.**

### Known gaps, not blocking

- The TUI renders a three-level tree flat. Cells are already keyed by
  `event.conversation_id`, so this is presentation only.
- `subagent_soft_max_steps` / `subagent_hard_max_steps` are a single flat pair
  applied at every depth. A three-deep tree multiplies total work with no
  per-depth budget. That gap is the argument for §2.

## 2. Max spawns per open turn

New config: `RuntimeConfig.subagents_max_per_turn: int = Inf`. The cap is
**per conversation, per open turn** — each subagent has its own turn and
therefore its own budget, and the count resets when the turn closes.

Enforcement is **two layers**, because one cannot cover the other's case:

| layer | where | covers | mechanism |
|---|---|---|---|
| **1 — the gate** (primary) | `spawn_gate_open` → `get_tools` + the prompt part | the budget is already spent when the tool list is built | the spawn tool and its prompt are **withheld**; the model never sees them |
| **2 — the runner** (fallback) | `_create_executions`' append loop | the budget runs out *inside* one assistant message, after the tool list was fixed | the overflow execution is **born terminal**; its body never runs |

Layer 1 is the normal path and does the work in almost every turn. Layer 2
exists for the one case layer 1 structurally cannot judge: the tool list is
decided *before* the model call, so if the model comes back with several spawn
calls at once, withholding has already happened and cannot un-happen.

### The shared counter

Both layers count the same thing, with one parameter that matters:

```python
def spawns_committed(
    session: AgentSession,
    conversation_id: str,
    *,
    exclude: str | None = None,
) -> int:
    """Subagents this conversation's OPEN TURN has already committed to.

    Counting rules, and why:

    - only spawn-DECLARING executions are counted; the budget is about
      subagents, not tool calls
    - a settled call counts only if it actually spawned — a spawn tool may
      return `is_subagent_spawn=False`, and a refusal is not a subagent
    - a call still in flight (PENDING / RUNNING) counts as ONE, reserved: it is
      about to become a child, and the budget must hold before the fact. If it
      ends up not spawning, the reservation is released simply by it becoming
      settled-and-not-spawned.

    `exclude` drops one execution id from the count. `_spawn_one` needs it —
    see "The self-counting trap" below.
    """
    nodes = session.conversations[conversation_id].nodes
    count = 0
    for execution in open_turn_executions(nodes, session.entries):   # models.py:806
        if execution.id == exclude:
            continue
        if execution.tool_spec is None or not declares_spawn(execution.tool_spec):
            continue
        if execution.status in (ExecutionStatus.PENDING, ExecutionStatus.RUNNING):
            count += 1                              # in flight — reserved
        elif spawn_payload(execution) is not None:
            count += 1                              # settled, and it spawned
    return count
```

It is a pure read over durable entries, so the count is rebuilt correctly after
a reload mid-turn — the same property the spawn handshake already relies on.
`declares_spawn` and `spawn_payload` exist today as `_declares_spawn`
(`runner.py:3632`) and `_spawn_payload` (`runner.py:3645`); both need to become
public so contrib can use them, along with `open_turn_executions`
(`models.py:806`), which is currently not exported from `luca.agent.core`.

### Layer 1 — the gate withholds

```python
# luca/agent/contrib/subagents/plugin.py:46
def spawn_gate_open(session: AgentSession, conversation_id: str) -> bool:
    config = session.session_config.runtime_config
    if not config.subagents_enabled:
        return False
    conversation = session.conversations.get(conversation_id)
    if conversation is None:
        return False
    if conversation.depth >= config.subagents_max_depth:
        return False
    # NEW — the per-turn budget. Inf by default, so this clause never fires
    # for a session that did not ask for a limit.
    return spawns_committed(session, conversation_id) < config.subagents_max_per_turn
```

Core's `_spawn_gate_open` (`runner.py:1739`) takes the identical clause. Both
must change together — they are one predicate written twice, and
`_verify_gate` exists precisely to catch them drifting apart.

What the model sees: at the step where the budget runs out, `get_tools` stops
returning `spawn_subagent` **and** `spawning_prompt_part` stops contributing
the "you can spawn subagents" instructions. Nothing errors; the capability
simply is not on the table. When the turn closes, the count resets and both
come back.

Because step 4 of the drive loop only runs when every execution is terminal,
`spawns_committed` at gate time never has an in-flight reservation in it — the
gate and the runner always agree about the number.

### Layer 2 — the runner refuses at birth

```python
# runner.py, inside _create_executions' append loop
for tc, (draft, exception) in zip(message.tool_calls, drafts, strict=False):
    doom_flagged = self._is_doom_loop(conversation_id, tc)

    # NEW — the budget the tool list could not enforce. Sequential by
    # construction: calls 1…k-1 of this same assistant message are already
    # appended, so the count below sees them as in-flight reservations.
    refusal = self._spawn_budget_refusal(conversation_id, draft)

    def build(entry_id, parent_id, ts, _draft=draft, _d=doom_flagged, _r=refusal):
        update = {
            "id": entry_id,
            "parent_id": parent_id,
            "created_at": ts,
            "conversation_id": conversation_id,
            "is_doom_loop_flagged": _d,
        }
        if _r is not None:
            update |= {"status": ExecutionStatus.REFUSED, "error": _r}
        status = update.get("status", _draft.status)
        update["ended_at"] = ts if status != ExecutionStatus.PENDING else None
        return _draft.model_copy(update=update)

    execution = self._append(conversation_id, build)
    ...
    if execution.status != ExecutionStatus.PENDING:      # existing branch, unchanged
        _, event = self._finalize_undispatched(conversation_id, execution, exception)
```

```python
def _spawn_budget_refusal(self, conversation_id: str, draft: ToolExecution) -> ToolExecutionError | None:
    """None if this call may spawn; the durable error to be born with if the
    open turn has spent its budget."""
    if draft.tool_spec is None or not declares_spawn(draft.tool_spec):
        return None
    limit = self.session.session_config.runtime_config.subagents_max_per_turn
    committed = spawns_committed(self.session, conversation_id)
    if committed < limit:
        return None
    return ToolExecutionError(
        error_type="SpawnLimitReached",
        error_message=(
            f"Spawn limit reached ({committed}/{limit} subagents this turn). "
            f"Complete the remaining work yourself; do not retry."
        ),
        details={"limit": limit, "committed": committed},
    )
```

The refusal is decided **before either body runs**, so dispatch order, dispatch
concurrency and how long each tool takes are all irrelevant. The only ordering
it relies on is the append loop's, which is inherent to persisting executions
in model-request order.

### The worked example — the case layer 1 cannot catch

`subagents_max_per_turn = 30`. This conversation's open turn has already
spawned 29 subagents across earlier steps. The model returns **one assistant
message with two `spawn_subagent` calls**, `tc30` and `tc31`.

| # | what happens | `spawns_committed` | outcome |
|---|---|---|---|
| 0 | the tool list for this step was built when the turn had 29 | 29 | 29 < 30 → **layer 1 allows it**; `spawn_subagent` is offered, correctly |
| 1 | the model returns `tc30` and `tc31` in one message | — | layer 1 is now spent; it cannot revisit a list already sent |
| 2 | drafts for both are gathered concurrently from the registry | — | two PENDING drafts; nothing written to the session yet |
| 3 | append loop, call 1 of 2: `tc30` | 29 settled | 29 < 30 → born **PENDING**, dispatched normally, spawns a child |
| 4 | append loop, call 2 of 2: `tc31` | 29 settled **+ 1 in flight** (`tc30`, appended a moment ago) = 30 | 30 ≥ 30 → born **REFUSED** by layer 2; body never runs |
| 5 | `_spawn_children` after the batch | — | one payload → exactly **one** new child |
| 6 | next model call | 30 | `tc30` → "Spawned subagent: …"; `tc31` → "Spawn limit reached (30/30 subagents this turn). Complete the remaining work yourself; do not retry." |
| 7 | the step after that | 30 | 30 ≥ 30 → **layer 1 withholds**: no spawn tool, no spawn prompt |

That is what "one starts, the other is immediately marked as an error" looks
like in the data model — and note that the model gets told twice, in two
different registers: once as a tool result it must read, then by the capability
disappearing.

### The self-counting trap — `_spawn_one` must exclude itself

**This is a live bug in the naive version of this change, and it fires on the
happy path.**

`_spawn_one` (`runner.py:2604`) re-checks `_spawn_gate_open` at child-creation
time, because the depth cap must mean something at the moment a child actually
appears, not only where tools are advertised. Once the budget joins that
predicate, the check runs at a point where the execution being converted is
**already settled and already counted**.

Walk the 30th legitimate spawn with `subagents_max_per_turn = 30`:

1. 29 spawns settled in the open turn.
2. `tc30` is born, dispatched, and completes with `is_subagent_spawn=True`.
3. Step 2b: `_spawn_children` → `_spawn_one(tc30)`.
4. `_spawn_gate_open` → `spawns_committed` = **30** (29 settled + `tc30`, now
   settled and spawned).
5. `30 >= 30` → `_spawn_one` **raises `AgentError`** and kills the run — for a
   spawn that was correctly allowed by both layers.

Fix: `_spawn_one` passes the execution it is converting to `exclude`, so the
question it asks is "was there room for this one?", not "is there room for
another?".

```python
# runner.py:2604 — _spawn_one
if not self._spawn_gate_open(conversation_id, exclude=execution.id):
    raise AgentError(...)
```

`_spawn_gate_open` therefore grows an `exclude` parameter that it forwards to
`spawns_committed`. Every other caller passes nothing. Contrib's
`spawn_gate_open` does not need the parameter — no contrib caller converts an
execution — but keeping the signatures identical is cheaper than explaining
why they differ.

### Every scenario, and what happens

| # | scenario | result |
|---|---|---|
| S1 | budget available, one spawn call | normal spawn; count +1 |
| S2 | budget spent, new step | layer 1: tool and prompt part withheld; model cannot call it |
| S3 | budget runs out mid-message (29/30 above) | layer 2: first call spawns, overflow born REFUSED |
| S4 | exactly at the boundary — 29 spent, one call arrives | allowed (29 < 30), becomes the 30th; withheld from the next step on |
| S5 | spawn tool returns `is_subagent_spawn=False` | not counted; the budget is not consumed by a refusal |
| S6 | a spawn call is REJECTED by an approval policy | never produced a payload → not counted; the budget is not consumed |
| S7 | a spawn call FAILS or TIMES OUT | same — settled without a payload, not counted |
| S8 | reload mid-turn | `spawns_committed` is rebuilt from entries; both layers agree with the pre-reload state |
| S9 | the turn closes, a new one opens | count resets to 0; the tool and prompt come back |
| S10 | the 30th legitimate spawn reaches `_spawn_one` | must pass `exclude=execution.id` or it raises — see the self-counting trap |
| S11 | a subagent spawns its own subagents (depth ≥ 2) | it has its own conversation and its own open turn, so it gets its own full budget; the caps do not aggregate across the tree |
| S12 | `subagents_max_per_turn = Inf` (the default) | neither layer ever fires; nothing changes for existing sessions |
| S13 | a non-spawn tool call, at any count | never counted, never refused — the check reads the spec's declaration |
| S14 | a third-party registry that does not implement the budget | it keeps offering the spawn tool after the budget is spent, and `_verify_gate` raises. Same contract that already applies to the depth cap: a registry shipping spawn tools must build its tool list from `spawn_gate_open` (or reimplement all three clauses) |
| S15 | `subagents_enabled=False` or at the depth cap | those clauses short-circuit first; the budget never enters into it |

### The one data-model decision: a new terminal status

`ExecutionStatus` (`models.py:397`) is deliberately tight, and every existing
member would be a lie for a budget refusal:

| status | its documented meaning | why not |
|---|---|---|
| `REJECTED` | "the registry's `decide()` denied the execution" | no policy was consulted |
| `FAILED` | "tool-owned code raised" | no tool code ran |
| `INVALID` | arguments failed validation | the arguments were fine |
| `NOT_FOUND` | the tool could not be resolved | it resolved fine |

**Recommendation: add `REFUSED = "refused"` — "a framework runtime limit
refused the call before dispatch."** Honest, generalizes to the per-session cap
below and to any future framework-level refusal, and this is V1 so the enum is
free to grow.

What it touches:

- `ExecutionStatus`, plus the `ToolExecutionError` it carries — an error rather
  than a `STATUS_ONLY_OUTPUTS` entry is what lets the message name the actual
  numbers
- `DefaultConversationProjector._derived_failure_text` (`projection.py:493`):
  one branch rendering `error.error_message`, so the model reads the real
  reason instead of `[tool execution refused]`
- the TUI's tool-cell status rendering
- the status tables in `docs/agent/` and `AGENTS.agent.md`

**Alternative if a new status is unwanted:** `FAILED` carrying the same
`ToolExecutionError`. Zero data-model change, the model reads
`Tool execution failed: SpawnLimitReached: …`, and the only cost is that
`FAILED` stops strictly meaning "tool-owned code raised".

### Follow-on: per session

Per-turn resets every turn, so an agent in a loop can spawn 30 per turn
forever. Claude Code caps per session as well (200 by default). Same two
layers, wider window: `spawns_committed` over the whole conversation path
rather than the open turn, checked in the same two places, refused with the
same status.
